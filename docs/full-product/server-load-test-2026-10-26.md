# 服务端并发压测（2026-10-26）

## 结论

本轮用独立真实服务端进程、真实 WebSocket 和 M1 预组对局完成了文件存储档位 `N=1、5` 与一次独立的内存模式 `N=10` 对照。`N=5` 已满足用户给定的停止条件：聚合 p95 为 6,609.38 ms，超过 3 秒，而且 5 局中只有 3 局产生 winner；因此没有继续运行文件存储 `N=10、20、40`。

在当前共享开发机上，可复现且低于 3 秒 p95 的文件存储容量只有 **每个服务端进程 1 个同时对局房间（2 个客户端）**。这是实测上限，不是对未测档位的推算。`N=5` 的 p95 延迟约为 `N=1` 的 3 倍，内存模式 `N=10` 即使关闭文件存储仍有 4.63 秒 p95，主要瓶颈是单个 Node 服务端进程的 CPU/规则执行和整机争用，而不是 RSS 或磁盘容量。

## 瓶颈与容量建议

- **CPU/执行时间是第一瓶颈。** `N=1` 已出现近两个逻辑核的服务端进程峰值；`N=5` 峰值 268.11%，内存 `N=10` 峰值 269.95%。Node 主线程仍只有一个事件循环，采样超过 100% 来自该进程的多个线程，不能按 200% 理解为可并发两个独立主线程规则循环。
- **内存不是本轮首个限制。** RSS 从 `N=1` 的约 424 MB 峰值增长到 `N=5` 的约 593 MB，内存 `N=10` 约 591 MB。仍有可用量，但房间和匹配状态会随并发增长。
- **文件存储写入放大明显。** `N=1` 每局约 5.09 MB，`N=5` 每局约 4.61 MB；测试没有启用保留期清理，所以容量随对局数线性增长。按 4.6 MB/局粗估，10,000 局约 46 GB；部署应把日志保留、压缩/轮转和可用 inode 纳入容量规划。
- **共享机负载污染了绝对延迟。** 正式样本的 1 分钟 load 在 137–148 左右，测试期间整机 CPU 采样一度约 100%。这些数据适合当前主机上的保守容量判断，不能直接代表空闲生产机上的 SLO。

当前版本的推荐生产配置如下：

| 用途 | CPU | 内存 | 磁盘 | 单进程同时对局 | 余量判断 |
|---|---:|---:|---|---:|---|
| 已验证的保守部署 | 4 vCPU | 4 GiB | 50 GB NVMe/低延迟 SSD | 1 个房间（2 客户端） | CPU 实测峰值约 2 核，预留约 2 核；RSS 峰值约 0.4 GiB，预留约 10 倍 |
| 未验收的 N=5 候选 | 8 vCPU | 8 GiB | 100 GB+ NVMe/低延迟 SSD | 5 个房间（10 客户端） | 在干净主机、修复驱动并重跑前不推荐上线 |

如果要承载 40 个并发房间，按本轮已验证容量不能证明单实例可承载；应以“每个进程 1 个已验证房间”为下限做横向分片，并在独立机器上重新跑 5/10/20/40 后再决定能否合包。这个下限是按实测 SLO 得到的保守值，不是对共享机异常的永久结论。

## 方法和局限

- 脚本入口为 `apps/game-server/scripts/load-test.ts`，由 `tsx` 执行；每个档位启动一个真实的 `apps/game-server/src/index.ts` 子进程，从孩子进程 PID 读取 `/proc/<pid>/stat`，每 100 ms 采样 RSS 和进程 CPU。子进程通过 `PORT` 监听 `127.0.0.1` 的 35680–35699 内端口。
- file 档显式设置 `RIFTBOUND_STORAGE_DIRECTORY=/root/swarm-rift/shared/RIFT-1082-server-load-test/rooms-<N>`；memory 对照删除该环境变量。每个房间使用两个独立 WebSocket 客户端，分别提交 `rumble-sfd` 和 `fiora-sfd`、准备、按各自收到的私有 V2 投影换牌与发令，直到 `winnerPlayerId` 非空或命令/回合/时间预算耗尽。
- 每个房间的客户端种子为唯一的 `RIFT-1082-<roomIndex>`；服务端匹配的权威种子来自服务端生成的唯一 `roomId`，原始 JSON 对每局同时保存客户端 seed 和 `roomId`。
- 只有在收到对应 `command-receipt` 且两个客户端都观察到不早于该回执的投影后，才继续下一条命令；没有重连、伪造回执或手工改状态。命令上限 500、回合上限 40、单命令上限 30 秒、单局上限 780 秒。
- 服务端 CPU 百分比按 `/proc/<pid>/stat` 的用户态与内核态 ticks 计算，因此可超过 100%。机器 load average 和 `/proc/stat` 整机利用率一并保存在原始 JSON 中，用来解释共享机干扰。
- 原始证据位于：
  - `/root/swarm-rift/shared/RIFT-1082-server-load-test/formal5-20261026/file-n01.json`
  - `/root/swarm-rift/shared/RIFT-1082-server-load-test/formal5-20261026/file-n05.json`
  - `/root/swarm-rift/shared/RIFT-1082-server-load-test/formal5-20261026/report.json`
  - `/root/swarm-rift/shared/RIFT-1082-server-load-test/memory-n10-20261026/memory-n10.json`
  - `/root/swarm-rift/shared/RIFT-1082-server-load-test/memory-n10-20261026/report.json`
  - `/root/swarm-rift/shared/RIFT-1082-server-load-test/final-file-20261026/file-n01.json`

### 脚本用法

```bash
SWARM_TASK=RIFT-1082-server-load-test \
SWARM_PORT_BASE=35680 SWARM_PORT_SPAN=20 \
heavy env SWARM_TASK="$SWARM_TASK" \
  SWARM_PORT_BASE="$SWARM_PORT_BASE" SWARM_PORT_SPAN="$SWARM_PORT_SPAN" \
  apps/game-server/node_modules/.bin/tsx apps/game-server/scripts/load-test.ts \
  --modes=file,memory --levels=1,5,10,20,40 \
  --output-dir=/root/swarm-rift/shared/RIFT-1082-server-load-test/run \
  --max-commands=500 --max-turns=40 \
  --command-timeout-ms=30000 --game-timeout-ms=780000 \
  --startup-timeout-ms=180000
```

`memory` 模式固定使用 `N=10`。脚本在没有 `SWARM_TASK`、没有合法 `SWARM_PORT_BASE` 或试图跳过任务端口时直接报错；日志只输出到指定的 shared 目录。

## 产品缺陷与未完成项

- 未观察到服务端崩溃、非零退出、端口泄漏或客户端断线；所有已完成档位的服务端均被清理，端口已释放。
- 文件 `N=5` 有 2 局、内存 `N=10` 有 6 局停在“公开投影下无合法命令”。这可能是驱动 bot 无法构造更深层响应，也可能是投影/命令能力缺口；仅凭本轮无法证明是哪一方，因此不把它定性为确认产品缺陷，也不改产品代码。
- 内存 `N=10` 的 442 次战斗分配拒绝是压测 bot 的限制：服务端要求先给致命伤害后，bot 仍重复同一分配。该计数不能解释为 442 个独立服务端缺陷。
- 文件 `N=10、20、40` 未运行是用户规定的停止规则，不是跳过或隐藏失败；因此没有同并发文件/内存延迟差，只有内存 `N=10` 与文件 `N=5` 的参考数据。内存 `N=10` 的 p95 4.63 秒也说明即使去掉文件存储，当前实现仍未达到 3 秒目标。
- 未采集 CPU core profile、磁盘 IOPS/fsync 延迟和 GC 停顿；这些应作为下一次独立容量认证的补充指标。当前数据只能支持本机版本和本机负载下的容量结论。
