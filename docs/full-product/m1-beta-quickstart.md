# Riftbound M1 Beta 上手说明

适用范围：M1 Rumble（SFD）与 Fiora（SFD）两套预组的本地双客户端测试。

双方各使用一套 M1 预组，在本机用两个彼此独立的客户端窗口完成一局。当前仍是 beta 验证版，不代表完整官方规则已经验收。

## 1. 启动

需要 Node.js `^22.12.0 || ^24.0.0 || >=26.0.0`、pnpm `11.9.0`，并在仓库根目录准备好被 Git 忽略的卡牌目录数据。依次执行：

```sh
pnpm install --frozen-lockfile
pnpm cards:sync
scripts/beta/start-m1-beta.sh
```

启动器先检查运行环境、M1 牌表、`packages/card-data/data/deck-catalog.json`、存储目录和端口，再构建工作区、启动服务端与两个 Vite 客户端。它会等服务端健康检查、预组目录和两个页面都就绪，最长等待默认 180 秒；首次构建可能耗时数分钟。成功后会打印：

```text
客户端 A：http://127.0.0.1:5173/
客户端 B：http://127.0.0.1:5174/
V2 服务：ws://127.0.0.1:8787/ws
健康检查：http://127.0.0.1:8787/health
```

默认端口与服务地址：

| 项目 | 默认值 | 覆盖变量 |
| --- | --- | --- |
| 服务端 | `8787` | `RIFTBOUND_BETA_SERVER_PORT` |
| 客户端 A | `5173` | `RIFTBOUND_BETA_CLIENT_A_PORT` |
| 客户端 B | `5174` | `RIFTBOUND_BETA_CLIENT_B_PORT` |
| V2 WebSocket | `ws://127.0.0.1:8787/ws` | 随服务端端口变化 |
| 状态目录 | `.riftbound/m1-beta` | `RIFTBOUND_BETA_STATE_DIR` |
| 日志目录 | `.riftbound/m1-beta/logs` | `RIFTBOUND_BETA_LOG_DIR` |
| 房间数据 | `.riftbound/m1-beta/rooms` | `RIFTBOUND_STORAGE_DIRECTORY` |

查看状态或停止时：

```sh
scripts/beta/start-m1-beta.sh --status
scripts/beta/start-m1-beta.sh --stop
```

`--help` 还列出 `RIFTBOUND_BETA_VITE_CONFIG` 和 `RIFTBOUND_BETA_READY_TIMEOUT_SECONDS`。若改过端口，后续界面的服务地址和脚本打印的地址要使用同一组值。`--stop` 只停止本脚本在状态目录中记录的进程；不要按进程名或端口批量终止其他实例。

## 2. 打开两个玩家窗口

两名玩家必须使用独立的客户端存储上下文。两个不同端口的页面本身就是两个 origin，可以各开一个浏览器窗口；同一 origin 的多个标签页会共享本地会话。不要用同一 profile 的两个标签页代替两名玩家。

使用浏览器时，分别手动打开客户端 A 与客户端 B 的两个地址；启动脚本只打印地址，不会自动打开窗口。

使用 Mac 原生客户端时，先安装 macOS 上仓库锁定的 Rust `1.90.0`。保留第 1 步启动的 `5173` 客户端，再在仓库根目录执行：

```sh
pnpm desktop:dev
```

原生窗口固定连接 `http://127.0.0.1:5173`；另一名玩家打开 `http://127.0.0.1:5174/`。如果已经生成 release bundle，App 的相对仓库根路径是：

```text
apps/desktop-client/src-tauri/target/release/bundle/macos/Riftbound Desktop Client.app
```

按当前仓库配置生成的本地 App 没有签名，macOS 首次拦截时可在 Finder 中右键选择“打开”。原生 App 仍默认连接 `ws://127.0.0.1:8787`，所以启动 App 前要先完成第 1 步。仓库默认 bundle 目标仍是 Windows 的 `nsis`；需要另外显式使用 `--bundles app` 生成上述 macOS bundle。本次未在 macOS 真机复验该入口，因此原生 App 路径必须与双浏览器路径分别签收。

## 3. 连接并开一局

两个窗口都从首页进入“房间连接”，点击“使用协议 v2 独立房间”。在“V2 服务地址”中确认脚本打印的地址，再点击表单里的“连接”；页面显示“已连接”，并且“连接 V2 服务”按钮消失后，才进入房间入口。

客户端 A：

1. 在“玩家名”填写昵称。
2. 点击“创建 1v1 房间”。
3. 记下页面“房间”标题后的 8 位房间号，告诉另一名玩家。

客户端 B：

1. 填写自己的玩家名和 A 的房间号。
2. 点击“加入房间”。

双方进入房间后，各自由“M1 预组”下拉中选择 `rumble-sfd` 或 `fiora-sfd`，首选一方一套、彼此不同。脚本给服务端设置 M1 预组白名单，客户端也只提供这两项；其他牌组会被拒绝。随后每位玩家依次：

1. 点击“提交预组牌组”；成功后按钮停用，说明本席位已经提交。
2. 点击“准备”。双方提交预组并准备后，服务端按顺序开放换牌窗口。

当前 V2 页面的 `waiting` 和房间版本文本沿用协议值，不作为玩家界面的中文翻译判断依据。以服务端回执、当前投影与按钮启用状态为准。

## 4. 换牌与进入牌桌

服务端逐个开放换牌窗口。“我的手牌”会显示自己的起手；只有当前 owner 的选择控件可用。

- 不换牌：直接点击“保留起手”。
- 换牌：点选至多 2 张，按钮显示“换掉 N 张”时点击提交。
- 尚未轮到：页面显示“等待服务端开放你的换牌窗口。”

双方都确认后，服务端开始正式对局。可以点击首页的“继续对局”，或从顶部导航的“对局”进入牌桌。隐藏牌面只显示数量；资源、状态、事件序号和可执行操作都来自服务端投影。当前双浏览器 V2 完整对局仍以调度者最后的 LAND_CHECK 为准；本文没有把源码核对当作该门禁已经通过。

## 5. 对局操作

按钮可用只表示当前投影认为该命令可以被提交；最终结果以服务端回执为准。每个主要操作都会先进入应用状态，并显示“正在处理…请等待服务端回执；命令完成前，重复操作已停用。”，不要连续点击。

| 操作 | 页面路径 |
| --- | --- |
| 获取资源 | 在“符文”区对未横置符文点“取能量”或“取 Power” |
| 打出手牌 | 在“我的手牌”点牌，查看“出牌”中的“永久物落点”与目标要求，再点“打出手牌” |
| 移动单位 | 在“移动”中选单位、选“目的地”，再点“移动单位” |
| 让过优先权 | 在“对局操作”中点“Pass” |
| 推进任务 | 在“战斗”中点“推进” |
| 结束回合 | 在“对局操作”中点“结束回合” |
| 回答效果 | 在“选择请求”中选选项、排序、接受/拒绝或填数值，再点“提交选择” |
| 分配伤害 | 在“战斗伤害分配”里按显示预算填写各目标金额，再点“提交战斗伤害”；等待时显示“等待对方分配伤害” |
| 认输 | 点“认输”，再点“确认认输”；也可点“取消”返回 |

“链 / 优先权”显示服务端投影中的链状态、阶段、窗口、Priority 与 Focus。“选择请求”只有在服务端发给当前玩家时才可回答；候选缺失时客户端会等待投影，不会从隐藏手牌或其他对象自行推导。

命令被拒绝时，页面会显示“命令 … 未执行：<服务端原因>”；没有原因时显示“服务端未提供拒绝原因。”。传输错误和投影错误也会单独显示。不要绕过 ACK、手改状态或重复发送来继续。

## 6. 中途断开或重启

脚本默认把房间数据写入 `.riftbound/m1-beta/rooms`，并在重启时校验存档。停止脚本后再次执行启动器，重新打开两个独立客户端；V2 会使用保存的会话恢复身份并重新获取服务端投影。对局越长，首次恢复和重放可能越慢。

若页面在“连接中”和“重连中”之间循环，或恢复失败，先停止重复操作，记录房间号、连接状态、投影阶段、状态号与服务器日志。当前 V2 beta 的房间恢复仍应按失败关闭处理，不能用手改投影或重新伪造会话绕过校验。历史 readiness 记录中的 opening/waiting-room resume 问题对应 RIFT-1021；当前源码已有 waiting-room 与 setup 恢复测试，但本任务没有独立执行原生 Mac 或双浏览器重启验收。V2 自动捕获默认最多 4096 个投影帧，仍受本机最多 10 份回放记录的限制。

## 7. 已知问题

| 现象 | 当前状态与工单 |
| --- | --- |
| 双方确认起手后，要等约 6–8 秒才开局 | RIFT-1103 正在定位并优化；等待期间以“正在处理…”和服务端回执为准 |
| 战斗伤害分配期间，非分配方仍能点 Pass，点了不会推进对局 | 已查明为 bug，RIFT-1105 排队修复；当前不要用重复 Pass 尝试推进，记录战斗、Priority/Focus 与回执 |
| 每条命令回执约 0.1–1 秒，结束回合等重操作偏慢 | 性能已优化两轮；结构性优化排在 beta 之后 |
| 卡牌名称和效果说明是英文 | 沿用官方卡牌原文 |
| 两个客户端都停在“等待规则处理” | 极少数效果尚未接入；按 fail-closed 处理，不猜测结算。记录卡名和截图反馈 |

当前文档核对确认：V2 牌桌页仍依赖服务端发布的合法操作，尚未覆盖全部官方卡牌能力，也没有面向用户的完整 strict replay 验收；不要因按钮可点击就推定对应卡牌的全部官方能力已经完成。

## 8. 反馈时请提供

- 两个窗口的全页截图，包含房间号、回合、阶段、状态号和“最近的命令确认”。
- 操作步骤：点了什么、期望发生什么、实际发生了什么；命令拒绝时保留完整原因。
- 默认日志目录 `.riftbound/m1-beta/logs` 下的 `server.log`、`client-a.log` 和 `client-b.log`。
- Vite 或服务端启动失败时附上终端输出及脚本打印的日志目录。

不要把会话恢复令牌、密钥或其他个人信息写入 issue、聊天或公共日志。`rooms/` 下是私密房间归档，只交给项目维护者，并先遮蔽其中可能存在的恢复身份。
